# v2.5 Frontend Session Identity

## Scope

- Frontend login persists the authenticated `userId` together with the current session data, including token, role, and display name.
- Frontend API calls should prefer the current session identity when a student-owned or company-owned request needs `studentId` or `companyId`.
- Hardcoded demo identifiers such as `S001` and `C001` remain only as no-session demo fallbacks, not as the default identity source after login.
- The browser session becomes the frontend source of truth while backend services continue to enforce trusted identity through JWT and gateway-injected headers.

## Covered Flows

- Student session identity:
  - profile and resume actions use the logged-in student id when the API needs `studentId`.
  - match, delivery, and AI interview requests derive `studentId` from the current session before falling back to demo defaults.
- Company session identity:
  - job publishing, delivery review, and AI candidate screening derive `companyId` from the current session before falling back to demo defaults.
- Admin session identity:
  - admin views keep explicit query or route parameters for cross-role review workflows and do not silently rewrite target student/company ids.

## Verification

```powershell
cd frontend
npm run test:unit
npm run build
```

Manual browser UI check:

- Start the frontend in the normal local demo mode.
- Log in as student, company, and admin demo accounts.
- Confirm the browser session stores `userId`, token, role, display name, and session metadata after login.
- Exercise student-owned flows and verify request payloads use the logged-in student id instead of a static `S001`.
- Exercise company-owned flows and verify request payloads use the logged-in company id instead of a static `C001`.
- Confirm refresh/logout clears or replaces the active session as expected.
