# v3.2 Persistent AI Screening and Three-VM Acceptance

## Scope

- Added restart-safe async candidate-screening task persistence.
- Added MySQL table `ai_candidate_screen_task` for task state, original request snapshots, optional result snapshots, and RocketMQ dedup keys.
- Added startup recovery: persisted `PENDING` and `RUNNING` tasks become retryable `FAILED` tasks after `ai-service` restart.
- Added RocketMQ idempotency for `DELIVERY_CREATED` events by deriving a dedup key from `deliveryId`.
- Upgraded `scripts/check-three-vm-health.ps1` into the Windows-first acceptance entry for real three-VM deployment.
- Added checks for `vmrun`, VMX paths, VM running state, Compose config, VM IP connectivity, and key HTTP/TCP health endpoints.
- Added timestamped Markdown reports under `reports/deploy/three-vm-smoke-<timestamp>.md` with `PASS`, `FAIL`, and `SKIPPED` results.
- Documented the v3.2 real acceptance flow in `docs/deploy/three-vm-deploy.md`.

## Backend Behavior

- `CandidateScreenTaskService` now writes through `CandidateScreenTaskStore`.
- Local demo mode keeps bounded in-memory task storage.
- With `AI_SCREENING_PERSISTENCE_ENABLED=true` and datasource configuration, task state is stored in MySQL.
- Failed task retry uses the persisted `CandidateScreenRequest` snapshot, so retry still works after restart.
- RocketMQ duplicate delivery messages return the existing `ROCKETMQ` task instead of creating duplicate screening tasks.

## Database

- New table: `ai_candidate_screen_task`.
- Key fields: `task_id`, `delivery_id`, `company_id`, `student_id`, `resume_id`, `job_id`, `status`, `source`, `message`, `result_snapshot`, `request_snapshot`, `dedup_key`, `created_at`, `updated_at`.
- `dedup_key` is unique and nullable, allowing repeated manual tasks while preventing duplicate RocketMQ tasks.

## Script Usage

Dry-run:

```powershell
.\scripts\check-three-vm-health.ps1 -DryRun
```

Real acceptance with explicit VM inputs:

```powershell
.\scripts\check-three-vm-health.ps1 `
  -EnvFile .\deploy\three-vm.env `
  -Vm1Vmx "D:\Virtual_Machines\Ubuntu18_64_2\<vm1>.vmx" `
  -Vm2Vmx "D:\Virtual_Machines\ai-recruit-vm2\<vm2>.vmx" `
  -Vm3Vmx "D:\Virtual_Machines\ai-recruit-vm3\<vm3>.vmx" `
  -Vm1Ip 192.168.56.11 `
  -Vm2Ip 192.168.56.12 `
  -Vm3Ip 192.168.56.13 `
  -SshUser ubuntu
```

The script does not hardcode SSH passwords or application login passwords. SSH is not executed by default; report hints use the current `ssh` config or a user-provided key.

## Actual VM Smoke

The local VMware inventory was started with `vmrun` and the script was run against VMware Tools reported IPs:

- VM1: `192.168.6.130`
- VM2: `192.168.6.137`
- VM3: `192.168.6.138`

Report:

- `reports/deploy/three-vm-smoke-20260610-234906.md`

Result:

- `PASS=21`
- `FAIL=16`
- `SKIPPED=3`

Confirmed working:

- `vmrun` is available.
- All three VMX files exist.
- All three VMs were running.
- All three VMs responded to ping.
- All three Docker Compose VM files passed `docker compose config --quiet`.
- VM1 Gateway `/actuator/health`, Nacos HTTP, and Nacos gRPC were reachable.

Remaining deployment blocker:

- SSH key-based access from the Windows host was not available for the VM users.
- Non-interactive SSH probes with the current Windows host keys returned `Permission denied (publickey,password)` for VM1, VM2, and VM3.
- VM2 business service ports and VM3 infrastructure/AI ports were not reachable during the smoke run, so container startup inside those VMs still requires VM login access or a preconfigured deployment agent.
