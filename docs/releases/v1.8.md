# v1.8 Match Persistence and Cache

## Scope

- `match-service` supports optional MySQL persistence for resume-job match results.
- The default local demo still uses in-memory storage when `MATCH_PERSISTENCE_ENABLED=false`.
- Student match results, job candidate match results and all match results use Redis cache-aside when Redis is available.
- Creating a match evicts related student, job and all-results cache keys.
- Runtime database or Redis failures are logged and degraded so matching and query flows remain demo-usable.
- Single-machine Docker Compose and three-VM Compose can enable match persistence against MySQL/Redis.

## Configuration

- `MATCH_PERSISTENCE_ENABLED`
  - Default: `false`
  - Docker Compose default: `true`
- `SPRING_DATASOURCE_URL`
  - Example: `jdbc:mysql://mysql:3306/ai_campus_recruit?useUnicode=true&characterEncoding=utf8&serverTimezone=Asia/Shanghai&allowPublicKeyRetrieval=true&useSSL=false`
- `SPRING_DATASOURCE_USERNAME`
- `SPRING_DATASOURCE_PASSWORD`
- `SPRING_DATA_REDIS_HOST`
- `SPRING_DATA_REDIS_PORT`
- `MATCH_CACHE_TTL`
  - Default: `10m`
- `MATCH_CACHE_KEY_PREFIX`
  - Default: `match:results`
- `MATCH_DB_HEALTH_ENABLED`
  - Default: `false`
- `MATCH_REDIS_HEALTH_ENABLED`
  - Default: `false`

## Redis Keys

- `match:results:list:ALL`
- `match:results:student:{studentId}`
- `match:results:job:{jobId}`

When a match result is created, the service evicts:

- `match:results:list:ALL`
- `match:results:student:{studentId}`
- `match:results:job:{jobId}`

## Fallback

- Persistence disabled: use in-memory match results.
- Persistence enabled but datasource or mapper missing: use in-memory match results.
- Database read/write fails at runtime: fall back to in-memory results for that operation.
- Redis read/write/delete fails: log and continue with database query or save.
- DB and Redis health contributors are disabled by default so a missing local MySQL/Redis instance does not mark the demo service down.
