# v1.6 Delivery Persistence and Cache

## Scope

- `delivery-service` supports optional MySQL persistence for delivery records.
- The default local demo still uses in-memory storage when `DELIVERY_PERSISTENCE_ENABLED=false`.
- Company delivery lists use Redis cache-aside when Redis is available.
- Runtime database or Redis failures are logged and degraded so delivery creation, listing and status updates remain demo-usable.
- Single-machine Docker Compose and three-VM Compose can enable delivery persistence against MySQL/Redis.

## Configuration

- `DELIVERY_PERSISTENCE_ENABLED`
  - Default: `false`
  - Docker Compose default: `true`
- `SPRING_DATASOURCE_URL`
  - Example: `jdbc:mysql://mysql:3306/ai_campus_recruit?useUnicode=true&characterEncoding=utf8&serverTimezone=Asia/Shanghai&allowPublicKeyRetrieval=true&useSSL=false`
- `SPRING_DATASOURCE_USERNAME`
- `SPRING_DATASOURCE_PASSWORD`
- `SPRING_DATA_REDIS_HOST`
- `SPRING_DATA_REDIS_PORT`
- `DELIVERY_CACHE_TTL`
  - Default: `10m`
- `DELIVERY_CACHE_KEY_PREFIX`
  - Default: `delivery:records`
- `DELIVERY_DB_HEALTH_ENABLED`
  - Default: `false`
- `DELIVERY_REDIS_HEALTH_ENABLED`
  - Default: `false`

## Redis Keys

- `delivery:records:company:{companyId|ALL}`

When a delivery is created or its status changes, the service evicts:

- `company:ALL`
- `company:{companyId}`

## Fallback

- Persistence disabled: use in-memory delivery records.
- Persistence enabled but datasource or mapper missing: use in-memory delivery records.
- Database read/write fails at runtime: fall back to in-memory records for that operation.
- Redis read/write/delete fails: log and continue with database query or save.
- DB and Redis health contributors are disabled by default so a missing local MySQL/Redis instance does not mark the demo service down.
