# v0.8 AI Screening Persistence

## Scope

- AI 候选人筛选历史支持 MySQL 持久化。
- 筛选历史查询支持 Redis cache-aside 缓存。
- 默认仍使用内存仓储，避免本地无 MySQL/Redis 时阻断演示。
- 企业端筛选历史面板新增刷新按钮，可手动重新拉取持久化历史。
- Docker Compose 中 `ai-service` 默认连接 Compose 网络内的 MySQL 和 Redis。

## Configuration

- `AI_SCREENING_PERSISTENCE_ENABLED`
  - 默认：`false`
  - Docker Compose 默认：`true`
- `SPRING_DATASOURCE_URL`
  - 示例：`jdbc:mysql://mysql:3306/ai_campus_recruit?useUnicode=true&characterEncoding=utf8&serverTimezone=Asia/Shanghai&allowPublicKeyRetrieval=true&useSSL=false`
- `SPRING_DATASOURCE_USERNAME`
- `SPRING_DATASOURCE_PASSWORD`
- `SPRING_DATA_REDIS_HOST`
- `SPRING_DATA_REDIS_PORT`
- `AI_SCREENING_CACHE_TTL`
  - 默认：`10m`
- `AI_SCREENING_CACHE_KEY_PREFIX`
  - 默认：`ai:screening:records`
- `AI_SCREENING_DB_HEALTH_ENABLED`
  - 默认：`false`
  - 开启后 actuator health 会检查 MySQL；默认关闭，避免数据库临时不可用时阻断 AI 演示接口。

## Redis Keys

- `ai:screening:records:company:{companyId|ALL}:delivery:{deliveryId|ALL}`

When a new record is saved, the service evicts:

- `ALL/ALL`
- `companyId/ALL`
- `ALL/deliveryId`
- `companyId/deliveryId`

## Fallback

- Persistence disabled: use in-memory records.
- Persistence enabled but datasource or mapper missing: use in-memory records.
- Database read/write fails at runtime: fall back to in-memory records for that operation.
- Redis read/write/delete fails: log and continue with database query or save.

## Verification

```powershell
cd backend
mvn -s settings.xml.example -pl common,ai-service -am test

cd ../frontend
npm run test:unit
npm run build

cd ..
docker compose config --quiet
```

Runtime validation:

- Start MySQL and Redis.
- Start `ai-service` with `AI_SCREENING_PERSISTENCE_ENABLED=true`, datasource variables, and Redis variables.
- Call `POST /api/ai/candidates/screen`.
- Restart `ai-service`.
- Call `GET /api/ai/candidates/screenings?companyId=C001` and confirm the record is still present.

Validated on 2026-06-04 with temporary Docker containers:

- MySQL `mysql:8.4` on host port `3317`.
- Redis `redis:7-alpine` on host port `6380`.
- First `ai-service` run wrote `D-REAL-001` into `ai_candidate_screen_record`.
- Second `ai-service` run read the same `screeningId` from MySQL after restart.
- Redis generated `ai:screening:records:company:C-REAL-001:delivery:ALL`.
- Frontend production build was verified without chunk-size or `@vueuse/core` annotation warnings after route lazy loading and vendor chunk splitting.
