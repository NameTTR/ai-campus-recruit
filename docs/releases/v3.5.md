# v3.5 Three-VM AI Planning Persistence and Real Dashboard Acceptance

## Scope

- Completed the current round of three-VM integration acceptance coverage, including VM environment and compose updates for AI planning persistence, realtime dashboard aggregation, DashScope generation tuning, and user-service datasource access.
- Added DashScope temperature tuning through `DASHSCOPE_TEMPERATURE`; the AI client sends the configured value on chat completions and clamps invalid values into the `0`-`1` range.
- Changed the admin dashboard to aggregate real persisted tables when `DASHBOARD_REALTIME_ENABLED=true` and MySQL is reachable, while keeping the stable fallback dataset for disabled or unavailable realtime mode.
- Persisted student AI planning history for resume rewrite and career plan flows, exposed it through the backend API, and added frontend history display.
- Added frontend E2E smoke automation for the student planning and dashboard-facing acceptance path.

## API Contracts

- `GET /api/ai/career/history?studentId=S001&limit=20`
  - Returns `ApiResponse<List<AiPlanningRecord>>`.
  - `AiPlanningRecord` fields: `recordId`, `studentId`, `operation`, `resumeId`, `targetRole`, `resumeRewrite`, `careerPlan`, `mocked`, and `createdAt`.
  - `limit` defaults to `20` and is normalized to the `1`-`100` range.
  - When Gateway injects `X-User-Role=STUDENT` and `X-User-Id`, the injected identity overrides the `studentId` query parameter.

- `GET /api/admin/dashboard`
  - With realtime mode enabled and datasource access available, `user-service` aggregates `resume_summary_record`, `job_record`, `match_result_record`, `delivery_record`, `ai_candidate_screen_record`, and `ai_planning_record`.
  - If realtime aggregation cannot run, the response falls back to deterministic demo data instead of failing the admin screen.

## Database

- Added `ai_planning_record` for AI resume rewrite and career plan history.
- The table stores `record_id`, `student_id`, `operation`, optional `resume_id`, `target_role`, `response_snapshot`, `mocked`, and `created_at`.
- `response_snapshot` stores the structured AI response as JSON so planning history can survive `ai-service` restart when `AI_PLANNING_PERSISTENCE_ENABLED=true`.

## Deployment

- Related three-VM environment variables:
  - `AI_PLANNING_PERSISTENCE_ENABLED`: enables MySQL persistence for AI planning history in `ai-service`.
  - `DASHBOARD_REALTIME_ENABLED`: enables real MySQL aggregation for the admin dashboard in `user-service`.
  - `DASHSCOPE_TEMPERATURE`: controls DashScope generation temperature.
  - `SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME`, and `SPRING_DATASOURCE_PASSWORD` on `user-service`: provide VM3 MySQL access for dashboard aggregation.
- Real credential values must stay outside documentation and source control.
