# v1.7 Job Persistence and Cache

## Scope

- `job-service` supports optional MySQL persistence for job records.
- The default local demo still uses in-memory storage when `JOB_PERSISTENCE_ENABLED=false`.
- Job lists use Redis cache-aside when Redis is available.
- Creating a job or running AI job analysis evicts the job list cache.
- Runtime database or Redis failures are logged and degraded so job publishing, listing, detail and analysis remain demo-usable.
- Single-machine Docker Compose and three-VM Compose can enable job persistence against MySQL/Redis.

## Configuration

- `JOB_PERSISTENCE_ENABLED`
  - Default: `false`
  - Docker Compose default: `true`
- `SPRING_DATASOURCE_URL`
  - Example: `jdbc:mysql://mysql:3306/ai_campus_recruit?useUnicode=true&characterEncoding=utf8&serverTimezone=Asia/Shanghai&allowPublicKeyRetrieval=true&useSSL=false`
- `SPRING_DATASOURCE_USERNAME`
- `SPRING_DATASOURCE_PASSWORD`
- `SPRING_DATA_REDIS_HOST`
- `SPRING_DATA_REDIS_PORT`
- `JOB_CACHE_TTL`
  - Default: `10m`
- `JOB_CACHE_KEY_PREFIX`
  - Default: `job:records`
- `JOB_DB_HEALTH_ENABLED`
  - Default: `false`
- `JOB_REDIS_HEALTH_ENABLED`
  - Default: `false`

## Redis Keys

- `job:records:list:ALL`

When a job is created or analyzed, the service evicts the list cache.

## Fallback

- Persistence disabled: use in-memory job records.
- Persistence enabled but datasource or mapper missing: use in-memory job records.
- Database read/write fails at runtime: fall back to in-memory records for that operation.
- Redis read/write/delete fails: log and continue with database query or save.
- DB and Redis health contributors are disabled by default so a missing local MySQL/Redis instance does not mark the demo service down.
