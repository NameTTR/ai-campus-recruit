# v3.0 AI Async Candidate Screening

## Scope

- Added backend async screening task APIs in `ai-service`.
- Added a bounded in-memory async task queue that writes completed results to the existing candidate screening history.
- Added optional RocketMQ consumption for `delivery-events`, so `DELIVERY_CREATED` can trigger AI screening tasks in Compose or three-VM deployment.
- Added frontend client support for asynchronous candidate-screening tasks.
- Updated the company delivery review action from synchronous AI screening to asynchronous screening task creation.
- Updated the company AI screening history view to show task status, source, message, timestamps, and completed screening results.
- Kept deterministic frontend fallback tasks so Vite demo mode remains usable without a backend, gateway, or AI proxy.

## APIs

- `POST /api/ai/candidates/screen/tasks`
  - Request body: `CandidateScreenRequest`.
  - Response: `ApiResponse<CandidateScreenTask>`.

- `GET /api/ai/candidates/screen/tasks?companyId=C001&deliveryId=D001`
  - Query parameters: `companyId` and `deliveryId` are optional.
  - Response: `ApiResponse<CandidateScreenTask[]>`.

`CandidateScreenTask` fields:

- `taskId`
- `deliveryId`
- `companyId`
- `studentId`
- `resumeId`
- `jobId`
- `status`: `PENDING`, `RUNNING`, `COMPLETED`, or `FAILED`
- `source`: `DEMO`, `RUNTIME`, or `ROCKETMQ`
- `message`
- `result`: optional `CandidateScreenResult`
- `createdAt`
- `updatedAt`

## Frontend Behavior

- Company delivery review uses `createCandidateScreenTask()` and keeps the existing per-delivery loading state.
- The AI screening history page uses `listCandidateScreenTasks()` and sorts tasks by `updatedAt`.
- Completed tasks render the same structured result sections as before: score, recommendation, strengths, risks, interview questions, and next actions.
- Pending, running, and failed tasks render a compact status message without requiring `result`.
- Mobile layout keeps task metadata and result lists wrapping inside the card.

## Security

- The frontend does not hardcode AI credentials.
- `ai-service` keeps `AI_SCREENING_ROCKETMQ_ENABLED=false` by default for local development; Compose and three-VM deployment enable it explicitly.
- RocketMQ configuration is read from environment variables: `ROCKETMQ_NAME_SERVER`, `DELIVERY_EVENTS_TOPIC`, and `AI_SCREENING_ROCKETMQ_CONSUMER_GROUP`.
- Documentation examples do not include API keys, tokens, raw prompts, or full resume text.
- Public API responses continue to use `ApiResponse<T>`.
